## D9 — In-house Elo formulation + constants (Phase 2a) — **RATIFIED (owner, 2026-07-03)**
**Date:** 2026-07-03
**Context:** SPEC §6.1/§16.4 require an in-house, transparent Elo (not a public-rating blend). The constants must NOT be borrowed from another sport's Elo — FiveThirtyEight's NFL model starts from carried-over priors and only needs small in-season corrections; a flat-prior, current-season-only, ~12-game CFB system is the opposite regime, and a naive K=20 compresses ratings so badly the model-vs-market diagnostic becomes noise (invisible until October).
**Decision (structure — fixed):** classic Elo (400-scale logistic), completed 2026 games only (never seeded from 2025), MOV dampener `ln(|margin|+1)·mov_c/(mov_b·|ΔR_winner|+mov_c)`, **decaying K** `K(n)=k_late+(k_early−k_late)·exp(−n/k_decay_games)` (n = the two teams' avg games played; shares the games-played curve with D11), zero-sum updates (mean stays at baseline 1500), determinism via completed-only games sorted by `(week, start_date, home, away)`.
**Proposed constants** (`EloConfig`, `engine/power_ratings.py`), gated by the dispersion acceptance test and recorded in `CALIBRATION_LOG.md`: `k_early=64, k_late=22, k_decay_games=6, mov_c=2.2, mov_b=0.0018, hfa_elo=50 (=2.5 pts), elo_per_point=20`. Dispersion evidence: synthetic double round-robin (7 teams, true strengths −15…+15, incl. strong-vs-strong) recovers **30.8 pts** top-vs-bottom neutral (band 24–40), rank-fidelity r=0.998; naive K=20 gave ~19.7.
**Governance:** calibration is owner-only (§14.3). Proposed with the dispersion-test evidence and **ratified by the owner 2026-07-03** (CALIBRATION_LOG entry marked RATIFIED). Frozen at `v2026-frozen`.

## D15 — Decomposed-and-shared pricer + circularity prohibition (Phase 3a) — **CONFIRMED (owner)**
**Date:** 2026-07-03
**Context:** Phase 2's pricer applies schedule intel (bye/short-week/travel/altitude) to the model spread; Phase 3 adds physical FACTORS that adjust the Vegas line for the contrarian bet. The pricer is diagnostic-only in 2026 (factors alone drive recommendations), so there is no double-count in the bet. The real trap is SPEC §6/§7's **model-vs-market gap as a confirming signal** (the L2 fix): if the model spread contains the same bye/travel adjustment, using the gap to confirm a schedule factor is **circular** — confirming a signal with itself.
**Decision (owner, via the Phase-3 plan):**
1. **Decompose, don't merge or delete.** `engine/matchup_pricer.price()` returns a decomposed spread: `base` (Elo diff + HFA — team quality only), `schedule_adjustment` (physical), `total = base + schedule_adjustment` (test-pinned: `base_margin + schedule_component == home_margin`).
2. **Consumers pick the honest lane:** hypothetical mode → `total` (travel must show); the model-vs-market diagnostic → the **`base` gap** (`base_spread − vegas`; the total gap is logged too, LABELED); any Phase-3 **confirming-signal rule → the `base` gap ONLY, never `total`**.
3. **Explicit circularity prohibition (written rule + test):** *a schedule/physical factor must not be confirmed by a gap that contains the same schedule signal.* The `base` gap excludes schedule → satisfies it by construction. The engine exposes `model_vs_market_gap` = **base** gap (the only gap a confirming rule may use) + `model_vs_market_gap_total` (labeled, diagnostic-only). A test proves the two differ when schedule fires and that the confirming lane reads base.
4. **One source of truth for schedule coefficients:** Phase-3's calibrated schedule coefficients **supersede** the 2a `ScheduleAdjustmentConfig` (as CALIBRATION_LOG promised); the pricer's `schedule_adjustment` consumes those same values — **no parallel copy**. Both lanes freeze together at the tag. *(Sequencing: the decomposition landed in 3a while 2a is unfrozen; the coefficient relocation to the factor-owned source lands in 3b with the physical factor that becomes the second consumer — the single meaningful move point, avoiding a throwaway 3a rename.)*

## D17 — 2025 baseline regraded; the 57% headline was a measurement artifact — **RATIFIED (owner, 2026-07-03)**
**Date:** 2026-07-03
**Context:** The 2025 scorecard reported **57.0% ATS / +8.82% ROI** (SPEC §2, README, `scripts/calculate_accuracy.py` + `calculate_roi.py`). The Phase-3a calibration harness independently graded the same 300-game archive at **46.6% ATS**, and the two numbers sat unreconciled — including, briefly, both in the README's front door.
**Investigation:** graded the archive under both conventions side by side (both use the canonical cover rule `home covers S iff (home_score−away_score)+S>0`):

| bet side \ graded against | model's contrarian spread | Vegas line |
|---|---|---|
| **always home** | **57.0%** (171/300) | 54.4% (160/294) |
| **model's pick side** | 45.0% (135/300) | **46.6%** (137/294) |

**Finding:** the 57% comes from the win condition "the **home** team covered the model's **own** contrarian spread" — it always bets home and grades against the model's own number, not the market. That is a home-rating **bias diagnostic, not a placeable bet**. Graded as the actual contrarian strategy (the model's `edge_direction` side vs the Vegas line), 2025 was **46.6% ATS / −11.0% ROI** (294 graded bets, 6 pushes; 95% CI ~41–52%) — below the ~52.4% break-even. No subset rescues it: contrarian-edge-only games are 46.5%, and the contrarian picks (46.5%) matched the consensus games (46.7%), i.e. the contrarian adjustment added no value.
**Decision (owner-ratified 2026-07-03):**
- The honest 2025 baseline is **46.6% ATS / −11.0% ROI**. SPEC §2 and the README are corrected to lead with it.
- Each L1–L4 lesson is restated in SPEC §2 with its post-regrade status: **L4 strengthened**, **L3 partial** (compressed but real ranking signal), **L2 not isolable**, **L1 unverified** — physical weights rest on documented reasoning, not 2025 authority, and **3b calibration entries citing 2025 performance must use the post-regrade evidence**.
- The buggy scripts are **relabeled** in a follow-up PR (not silently fixed): keep the always-home diagnostic under an honest name (`home_vs_model_spread_diagnostic`), and make the default "ATS" path measure the placeable strategy. Deleting the old convention would orphan the explanation of where 57% came from.
**Why it's in the log:** the project's thesis is "can it beat the line without fooling itself." Here its own measurement infrastructure regraded its headline claim and found it didn't hold; the correction is published, with commits to prove it. The model is worse than yesterday's story and the project is stronger for proving it — and this entry is the audit-trail artifact the whole system exists to produce.

**Context:** The 3b review surfaced that `MarketSentimentCalculator` never set `is_multiplicative`; investigation found three coupled defects (all pre-existing) that together were the mechanical root cause of the D17 artifact (see the D17 addendum).
**Decision:**
- **Multiplicative, used directly, on the edge only.** `is_multiplicative = True`; the value is the multiplier (no re-centering); it scales **`total_adjustment` only** — `contrarian = vegas + total_adjustment · m`, never `(vegas + total_adjustment) · m`. Sentiment may amplify/dampen the model's *disagreement* with the market; it must never rescale the market's own number.
- **MODIFIER factors are weightless by design.** `self.weight` is inert for modifiers (`get_dynamic_weight` returns 1.0); a modifier is calibrated by its **range**, not a weight, and is excluded from additive-budget accounting.
- **No fabrication (#4).** The team-name MD5 hash and the spread/week "characteristic" heuristics — signal manufactured from nothing — are removed.
- **Dormant until real data.** With line-movement history deferred to slice 1.5 (D6), the factor returns neutral **1.0 (no effect)** whenever no real movement exists — the honest state of a factor whose inputs haven't arrived.
- **Range `[0.5, 1.5] → [0.85, 1.15]`** (`reasoned`): the ratified cap for when slice 1.5 brings real movement; a first-season, fabrication-history factor gets a tight cap, widened in 2027 with attribution.
**Evidence:** on the 2026 wk1 dry-run slate the fix removes a **+0.97-pt mean shift on 10/10 games**; edges collapse from ~1.0-everywhere to 0–0.15 (0 where no factor fires). Rerun is intentionally not bit-identical vs the old model; determinism within the corrected model holds.

## D17 addendum — root cause of the 2025 artifact identified (Bug #7) — **RATIFIED (owner, 2026-07-04)**
**Date:** 2026-07-04
D17 established that the 57.0% headline was a measurement artifact. This addendum records the **mechanical cause**, found while fixing the MarketSentiment wiring (D19).
**The 2025 "contrarian" model was a near-constant +1.0 shove, not a set of factor signals.** Across all 300 archive predictions, `contrarian_spread − vegas_spread` has **mean 0.986, median exactly 1.000, stdev 0.066**, and **300/300** games land within ±0.5 of +1.0. The constant is MarketSentiment's additive-vs-multiplicative bug (a 1.0-centered multiplier summed as points); the tiny stdev-0.066 wiggle around it was the now-removed team-name hash + spread/week heuristics. The factor system was otherwise effectively silent.
**It reconciles the D17 diagnostic table exactly** (always-home, canonical cover rule):

| always-home graded against | result |
|---|---|
| the model's contrarian spread | **57.0%** (171-129) |
| contrarian **minus the +1 phantom** | **54.2%** (161-136) |
| the Vegas line directly | **54.4%** (160-134) |

Removing the +1 collapses 57.0% onto the independent Vegas number — **the entire 57-vs-54.4 gap in the D17 table *is* the phantom.**
**edge_direction accounting.** All 300 signed edges are +1.0 (home-ward in spread space), yet the stored `edge_direction` splits 120 home / 180 away. That split is **100% determined by the sign of each game's Vegas line** (home-favored → "away" 180×; away-favored → "home" 113×; 7 boundary cases), i.e. the constant phantom mechanically bets the underdog every game, refracted through which side the line favored. It was never a directional signal.
**L3/L4 restatement.** The 2025 confidence and edge distributions L3/L4 rested on were phantom-contaminated: the "155-ish sub-1pt / rest 1–2pt" edge bucket (**0 games above 2pt**) was the constant, not hundreds of real marginal disagreements. Their *directives survive as design principles* — L4: don't fire on marginal edges; L3: confidence should rank ATS — but their **"2025 evidence" is now understood as measurement of the bug**, not of the market. Per the 3c constraint, the harness's confidence→ATS and edge→ATS tables may NOT be cited as measured evidence.
**Why it's in the log:** D17 said the headline was an artifact; this says *why*, and proves it to the decimal. Bug #7 — the most explanatory finding yet: the 2025 model wasn't a weak contrarian edge, it was one wiring bug applied 300 times.

## D22 — Grading writes a separate artifact; prediction files are byte-immutable forever — **RATIFIED (owner, 2026-07-09)**
**Date:** 2026-07-09
**Context:** Schema v2 (D21) defined `closing_spread`/`clv`/`graded_at` as fields **inside** the prediction record, "filled at grading in Phase 4." But `data/predictions/` is append-only (binding #5, immutable-history hook), and filling those slots means **editing an existing prediction file** — a real contradiction surfaced at the Phase-4 planning gate (the "adopt a data model without its storage answer" trap).
**Decision (owner, resolving the contradiction):** **Option B — prediction files are byte-immutable forever; grading never touches `data/predictions/`.** The pre-kickoff prediction commit is the **pre-registration artifact**, and its strongest form is byte-identity: the file on disk equals the file committed before the game, verifiable by checksum without git archaeology. Grading instead writes a **separate append-only graded artifact** (`data/graded/2026_week_NN.json`, keyed by `game_id`, carrying `closing_spread`/`clv`/`graded_at`/`ats_result` — SCHEMA §3a). The "filled" schema-v2 record exists **only as an in-memory JOIN** (predictions ⋈ graded), produced by analytics and rendered in reports — never materialized back to disk. The prediction record's grading slots stay honestly **`null` on disk permanently**: predictions are claims, results are outcomes. This is a conscious interpretation of 3d's "filled at grading" language, recorded here so it's on the audit trail.
**Consequences (ratified in the same session):**
1. **`ats_result` is a NEW persisted field** (win/loss/push ternary) → the graded record is a new schema, defined **at birth** via propose→pause→ratify with its own golden example + parity test, exactly as schema v2 got. **`V2_RECORD_KEYS` and the v2 golden file do NOT change** (the null slots stay).
2. **CLV `null`, never `0.0`, for no-side (neutral) games** (f3): CLV is defined from the bet side's perspective; no side ⇒ no perspective ⇒ undefined ⇒ `null`. `0.0` means "our number exactly matched the close" and nothing else. Most `NO_BET` games have a hypothetical lean and grade normally (labeled `is_hypothetical`); only truly neutral no-lean games get `null`, their own selectivity bucket. `utils.prediction_schema.clv`'s neutral branch is corrected `0.0 → None` (freeze-exempt `utils/`).
3. **Reproducibility carve-out (doctrine):** predictions are deterministic from a frozen snapshot; **gradings are evented outcomes** stamped at wall-clock `graded_at` — the graded artifact is deliberately **not** part of the snapshot reproducibility contract (SCHEMA §3a). `data/graded/` is append-only (per-game entry immutable once graded, new games appended — `data/lines/` semantics) and added to the immutability hook.
**Storage choice (owner-delegated):** a **parallel graded store** rather than enriching `data/results/` — grading is idempotent + catch-up and CLV depends on the growing `data/lines/` series, so the derived grading decouples cleanly from the raw-finals writer (`data/results/` = "what the scoreboard said"; `data/graded/` = "what we computed").

## D23 — Artifact taxonomy: `reports/` are regenerable renderings, not append-only history — **RATIFIED (owner, 2026-07-09)**
**Date:** 2026-07-09
**Context:** A Phase-4 code review surfaced a contradiction: the immutability hook (`.claude/hooks/protect_immutable.py`) and SPEC §14.2 treated `reports/` as **append-only immutable history**, but SPEC §10.3 has the Sunday pipeline **regenerate** the weekly/season reports as new grading data arrives, and `scripts/build_reports.py` overwrites the fixed report filename. In-season weekly/season reports embed wall-clock `graded_at` + `model_version`, so they are non-deterministic — regenerating legitimately changes their bytes. Treating a regenerable rendering as immutable history is a category error and a live footgun for the Phase-5 pipeline's commit choreography.
**Decision (owner):** a three-tier artifact taxonomy, and `reports/` is dropped from the immutability hook:
- **Claims** — `data/predictions/` — **byte-immutable forever** (D22): a claim, once committed pre-kickoff, is never edited (checksum-verifiable pre-registration).
- **Outcomes + derived computations** — `data/results/`, `data/archive/`, `data/lines/`, `data/ratings/`, `data/projections/`, `data/graded/` — **append-only** (new files/entries added as they arrive; existing entries never edited). These record events/measurements as they happen.
- **Renderings** — `reports/` — **pure functions over the above, regenerable at will.** A rendering has no independent truth to protect; re-running the generator over the same artifacts reproduces it (deterministically for frozen inputs like the 2025 retro; freshly for in-season reports as data accrues). **A rendering's audit trail is git history** (each commit is a dated snapshot), not on-disk immutability. So `reports/` is **not** guarded by the hook.
**Scope:** removes `"reports/"` from the hook's `PROTECTED` tuple; refines **SPEC §14.2** (which listed `reports/` under "immutable history") and aligns with SPEC §10.3 ("regenerate reports"). Consistent with **CLAUDE.md binding principle 5**, which already lists only `data/predictions/`/`data/results/`/`data/archive/` as append-only (never `reports/`). `docs/SCHEMA.md` §3a states the taxonomy; the Phase-5 `docs/PIPELINE.md` must describe the pipeline's report-commit step in these terms (renderings regenerated + committed each run).

## D25 — Destructive shell commands are hook-denied; the protected-path list is shared, not duplicated — **RATIFIED (owner, 2026-07-25)**
**Date:** 2026-07-25
**Context (the incident):** during a pre-freeze review, the **`code-reviewer`** subagent — whose prompt says "You are READ-ONLY: never edit files, never commit" — executed `git checkout <sha> -- .`, writing to the working tree. It was a **no-op in the event** (the tree was already at that commit) and no work was lost, but it exposed a gap that had nothing to do with that agent's judgement: **its `tools:` grant includes `Bash`, and prose is not a permission.** An audit of all five project agents followed; it was written up as a working document and its outcome is retired into this entry, which is now the authoritative record. Result: only `code-reviewer` had a write-capable grant; **`calibration-auditor`** — the agent that gates the freeze tag — was already correctly limited to `Read, Grep, Glob`, and is unchanged.
**The larger gap the audit surfaced:** `data/predictions/` is byte-immutable forever (D22) and six further directories are append-only (D23), but that was enforced **only against `Edit`/`Write`**. `protect_immutable.py` matches `Edit|Write|MultiEdit|NotebookEdit` and keys off `tool_input.file_path`, which a shell command does not have, so **it never fired for Bash at all**; `guard_bash.py` covered only secret-staging plus `rm`/`rmdir`/`mv`. A command such as `git checkout <old-sha> -- data/predictions/` would have **reverted a committed pre-registration artifact and been blocked by neither hook.** The guarantee rested on nobody typing it.
**Decisions (owner):**
1. **Extend `guard_bash.py`** rather than use `permissions.deny` in `settings.json`: the project already owns the hook, and regex can distinguish `git checkout -- <pathspec>` (denied) from `git checkout -b <branch>` (allowed), which prefix-based permission rules cannot do cleanly.
2. **Destructive git is denied GLOBALLY, for every caller including the main session** — `git checkout` with a pathspec or a commit-ish, `git restore`, `git reset --hard`, `git clean -f`, `git stash pop|apply`, `git apply`. **Benign git stays allowed:** `checkout -b`, plain branch switching, `diff`, `log`, `show`, `status`, `stash list`, `add`, `commit`, `push`.
3. **In-place file mutation stays SCOPED to the protected directories** — `rm`/`rmdir`/`mv`/`cp`/`dd`/`truncate`/`install`/`shred`, `sed -i`, `tee`, and `>`/`>>`/`>|` redirection targeting `PROTECTED`. **There is deliberately no global mutation block**; this mirrors the hook's existing posture.
4. **One `PROTECTED` tuple, shared not duplicated.** Extracted to **`.claude/hooks/protected_paths.py`**, imported by both hooks. A second copy is how two guards drift apart, and a drifted guard is worse than none because it reads as covered. Pinned by a test that fails if either hook defines its own copy.
5. **`code-reviewer` keeps `Bash`** — the hook now constrains it for all callers. Removing it would take away `git diff` (its primary input) and end its independent re-running of `make test` / `make lint` / the verify targets, which is precisely the "the author isn't the grader" property the checkpoint exists for.
**Stated threat model (added after three review rounds, and load-bearing):** this guard stops **accident and carelessness** — the actual incident was an agent casually running a destructive command, not evading a control. It is **not a security boundary against a caller deliberately working around it**, and cannot be: `eval`, base64, `python -c`, backtick substitution, and any alias defined in an earlier call all remain open **by construction**, because a `PreToolUse` string hook cannot interpret shell. **So does the whole class of filesystem-state-dependent bypasses** — `pushd`, subshells, symlinks and kin (owner ruling, 2026-07-26): the hook receives a string and has no filesystem state, and closing such instances one at a time is precisely the enumerated-set mistake this entry's own review record documents three times over. Representative cases are pinned in `tests/test_hook_guard_bash.py` as KNOWN-OPEN residuals, not as coverage. Known residuals are **pinned by tests as known**, never left to look like coverage. Anything stronger needs a sandbox, not a regex. **Considered and DECLINED (owner, 2026-07-25): a sandbox or a `permissions.deny` layer giving the categorical guarantee — disproportionate to the risk for a single-maintainer private repo whose real failure mode is a careless command, not an adversary. Recorded so 2027 does not re-litigate it from scratch.**
**Consequences:** a **225-case allow/deny matrix** (`tests/test_hook_guard_bash.py`) runs the real hook as a subprocess against real payloads — untested hook regex does not merge. **The review of this change returned NO-GO EIGHT times, and earned it every time.** Round 1: the implementation anchored on `git\s+<verb>`, so **one global option bypassed every destructive rule** (`git -C <dir> checkout -- data/predictions/` was ALLOWED), and an `=`-form flag defeated the commit-ish detection. Round 2 rejected the *fix*, correctly: enumerating the known global options closes the reported strings but not the **class** — any option outside the enumeration (`--no-optional-locks`, `-p`) silently defeated the whole rule again, and `git -c alias.co=checkout co …` defeated it through an option the fix had just whitelisted. **A closed set was the wrong shape for the problem.** The regex approach for git was therefore replaced outright: the command is split into clauses, each is tokenized, and **every token is scanned** for a destructive subcommand, so no verb position is assumed and an unknown option cannot shift the verb out of view; `-c alias.…` is denied outright. Re-reading that rewrite surfaced one more hole before review did — an unknown option taking a *separate value* makes positional parsing resolve the wrong token — which is why the scan is positionless. Round 3 found more, all closed: guard (c)'s regexes required a **trailing slash**, so `rm -rf data/predictions` — the more natural spelling — matched nothing and would have silently defeated the freeze-day extension to `factors/`; `dd`/`truncate`/`install`/`shred` and the `>|` clobber form were missing; `git config alias.…`, `$IFS`, `$(…)` substitution and backslash-newline continuation each defeated tokenizing; and the scan spuriously blocked `git log --grep revert`. **45 escapes are pinned as named regression cases** (`DENIED_GIT_ESCAPES`), each a demonstrated miss rather than a hypothetical. A guard shipped on its author's confidence would have read as protection while providing none, twice over — the exact failure this entry exists to prevent. **Round 4 found the round-3 fix repeating the round-2 mistake in a different place:** guard (c)'s terminator was *enumerated* (`/`, whitespace, quote, end-of-string) rather than bounded, so `rm -rf data/predictions; echo done` — ordinary shell punctuation, no evasion — walked straight past it, on the exact artifact this PR exists to defend. Replaced with a negative lookahead that closes the class, with sibling directories (`data/predictions_backup`, `data/predictions-old`) pinned as NOT swept in. **The lesson is now recorded twice over: an enumerated set is the wrong shape for a guard, and it failed here in two independent places before it was believed.** Side benefit: tokenizing removed the regex version's broad false positive (prose merely *mentioning* a denied command was blocked). **Five accepted over-blocks remain, each pinned or recorded as intended:** a heredoc line that itself begins with a denied command; prose containing the `$(` substitution form near a destructive verb (it blocked the PR description explaining that very rule); and reading *out* of a protected directory (`cp data/predictions/x.json /tmp/`), since distinguishing source from destination would mean encoding each verb's argument grammar — another enumerated set; and a glob under a protected root, which also catches globs under non-protected siblings of that root (`rm -rf data/snapshots/*`) and any glob whose typed prefix could expand to the root. **Rounds 5 and 6 were both the glob problem**: round 5 found that `rm -rf data/pred*` and `rm -rf data/{predictions,results}` reached the artifact without naming it, because the shell expands before the hook runs; round 6 found the fix for it *still* a literal-text rule, so `rm -rf dat*` and `rm -rf */predictions` walked past it, `sed -i`/`tee`/redirection were never covered at all, and `metadata/`/`validated_data/` were falsely blocked as substring matches. The glob check is now token-level, shared by every write context, and pessimistic by construction. Round 6 also caught **this entry itself** carrying a stale over-block count and NO-GO tally — the same stale-record failure it already documents twice. **Round 8 found the largest remaining gap, and it was not textual at all:** the guard never read `cwd`, while its sibling `protect_immutable.py` always had — so a shell standing in `data/` made a relative delete of `predictions` invisible. One ordinary `cd`, no evasion. |---|---:|

## D29 — The freeze gates read a PINNED tag-time vehicle, not the live week-1 snapshot — **RATIFIED (owner, 2026-08-07)**
**Date:** 2026-08-07
**Context:** Three `verify-phase-3` gates — the behavioural fingerprint (`eab7ffdb…20e2d` over 330 games), the L4 all-NO_BET slate assertion, and the 3d schema-v2 golden reproduction — plus `tests/test_golden_byte_identity.py` all read **`data/snapshots/2026_week_01/snapshot.json`**. That path is a **live** bundle: `data/snapshots/` is committed but **not** in `PROTECTED`, and `data.snapshot.store.write_snapshot` overwrites unconditionally. Phase 5's week-1 Tuesday run (`python scripts/build_snapshot.py --week 1`, live **2026-08-25**) therefore replaces the tag-time vehicle with a freshly-fetched one carrying live betting lines and accumulated team stats. The fingerprint would move, and all four gates would report "model output moved" **because the pipeline merely ran**. Found during Phase-5 planning by tracing the pipeline's first step against the gate's input, not by a gate failing.
**Decision (owner):** **The gates read a byte-for-byte copy of the tag-time snapshot, pinned under the append-only tier** at `data/archive/frozen/2026_week_01_snapshot.json`.
- **The fingerprint constant `eab7ffdb90df6fb549bbed0f9ebc291e00f710f592bc4e3699e41a3f52a20e2d` is UNCHANGED, and is never to be updated.** Verified after the move: the pinned vehicle reproduces it exactly, 330 games.
- **Why the read path may move when the constant may not.** The constant encodes *what the frozen model produces*. The vehicle is the *input it is measured on*. Letting the pipeline rewrite that input does not make the gate stricter — it makes it meaningless, because the gate would then be measuring the week's live data rather than the model. Moving the read path restores the gate's original meaning; updating the constant would destroy it. These are not the same act and must not be confused, which is why this entry exists.
- **The gate keeps its full sensitivity — verified, not assumed.** It re-runs the frozen `PredictionEngine` over the pinned input; it does **not** replay a stored result. So a change reaching output through the freeze-exempt **read seam** — `data/normalize/*`, `data/schedule_intel`, `data/venue_timezones`, the team registry, `config.py` — still moves the fingerprint and still trips the gate. That is precisely the class the pin must not weaken: it is how A6 (elevation metres-vs-feet) and the venue-timezone fallback both moved output after ratification. What the pin removes is only the *input churn* the pipeline itself introduces.
- **Provenance is proven, not assumed (owner precision requirement).** The bytes are extracted with `git show v2026-frozen:data/snapshots/2026_week_01/snapshot.json`, **not** copied from the working tree — `main` had already moved 3 commits past the tag. `tests/test_frozen_vehicle.py` **re-derives the SHA-256 from the tag on every run** and asserts byte equality, so "these are the tag-time bytes" is a checked claim. Pinned: `5c2c50ba97ebffa40810d4506771773334af9a41f393155fec7f8a3943ef318f` (445,433 bytes). *(Measured: the tag-time and working-tree bytes were in fact identical — but that was the assumption under test, and it is now enforced rather than relied upon.)*
- **Two failures, distinguishable.** The vehicle's own SHA-256 is asserted **before** the fingerprint, so "the gate's input changed" and "the model's output moved" report as different failures with different instructions. A single blended failure would send the reader to the wrong response.
**Implementation:** one accessor, no second copy to drift — `data.snapshot.store.{FROZEN_VEHICLE, FROZEN_VEHICLE_SHA256, FROZEN_VEHICLE_SOURCE, load_frozen_vehicle, frozen_vehicle_sha256}`, imported by `verify_phase_3.py`, `slate_fingerprint.py` and both tests.
**One trap found while implementing, recorded because it is silent:** `PredictionEngine` loads its own snapshot through `data.data_manager`, so handing a bundle to `analytics.predictions.build_predictions` redirects **enumeration only** — pricing still reads whatever is on disk. Every gate call site must wrap the engine call in `scripts.slate_fingerprint.engine_reads(bundle)` or it gets a **split read** (enumeration pinned, pricing live) that looks correct and is not. The redirect is factored into that one context manager for this reason.
**Scope:** freeze-exempt files only (`scripts/`, `tests/`, `data/snapshot/store.py`). `factors/`, `engine/` and every calibration constant are untouched.
